# TS-02 — Refresh Token 회전 경쟁 조건 및 로컬 테스트 전송 장애

## 1. 경쟁 조건의 위험과 해결

동일 refresh token을 병렬 요청에서 검사만 하고 개별적으로 갱신하면 둘 다 통과하거나 폐기된 family가 재활성화될 위험이 있다. 이는 설계 단계에서 식별한 위험이며, 기존 취약 구현의 실측 결과는 아니다.

MySQL refresh family 행 잠금으로 갱신과 재사용 검출을 직렬화했다. 토큰 원문 대신 SHA-256 해시를 저장하며, 재사용 시 family 전체를 폐기하고 트랜잭션을 커밋한 다음 HTTP 401을 반환한다. 프론트엔드는 single-flight와 동일 origin Web Locks로 불필요한 동시 갱신을 줄인다.

격리 Docker 환경에서 동일 토큰 동시 요청을 실행한 결과 한 요청만 성공했으며 재사용 검출 이후 새 토큰까지 폐기되었다. 마지막 관리자의 동시 강등 방지도 통과했다.

## 2. 실제 테스트 전송 장애

Windows 호스트 포트 경유 HTTP 통합 검사가 서로 다른 요청에서 WinError 10054로 두 차례 중단됐다. API 컨테이너는 healthy 상태였고 OOMKilled=false였다. 확인된 로그에 서버 예외는 없었으나 이것만으로 호스트 네트워크의 원인을 확정할 수는 없다.

별도 Compose 프로젝트의 Docker 내부 네트워크에서 같은 HTTP 시나리오를 실행했다. 테스트 스크립트의 CSRF 쿠키 갱신 시점 문제도 발견해 인증 POST 직전 토큰을 다시 읽도록 수정했다. 실제 브라우저 클라이언트는 이미 이 방식이었다.

## 3. 검증 결과와 남은 문제

- 격리 네트워크 HTTP 통합 11개 그룹 성공(종료 코드 0).
- Redis 중단 시 로그인 503 및 재기동 성공.
- 격리 테스트용 DB/볼륨만 제거; 일반 개발 DB 보존.
- Windows 호스트 TCP reset의 근본 원인은 미확정이다. 내부 네트워크 통과를 호스트 경유 전체 E2E 통과로 표현하지 않는다.
