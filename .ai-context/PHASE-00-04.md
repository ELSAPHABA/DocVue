## Phase 00 and original project definition

The user wanted a video learning platform that demonstrates technical problem solving across Spring MVC and WebFlux, Angular/RxJS, Vue, relational and reactive data, AWS/Ubuntu and later advanced native/legacy topics. The central product innovation is reproducible Docker environments per video segment, not simply hosting videos or teaching syntax. Early architecture distinguished S3 blob storage from a real OCI Distribution API, and mutable source workspace from read-only image. The final approved approach is in D00-01–08 (see main context and Technical_Contracts.md); no cloud costs approved.

## Phase 02 — identity and tenant authorization

User authorized Phase2. Implemented Spring Security resource server RS256 JWT, JWKS rotation, Argon2id, email code/invitations, refresh family rotation and strict replay detection, tenant membership, role/approval, audit, Redis Lua rate limit, Angular/Vue AuthPanel and common AuthClient. V2 migration added 9 tables: users, tenants, memberships, email_verifications, refresh_families, refresh_tokens, invitations, idempotency_keys, audit_events. Kept V1 immutable. Explicit row locks/conditional SQL with JdbcTemplate; JPA remains for later content. Tests cover actual DB and Mailpit. See ADR-0006/Phase_02_Identity.md. No external email delivery. Production private keys passed as paths to PKCS8/X509 files, optional previous public key; no private key in JWKS. Only dev ephemeral keys and nonsecure cookie HTTP. Require SMTP STARTTLS in production. Current user password/reset recovery absent.

Contract details:
- Generic duplicate registration 202; normalized unique ASCII email; no account enumeration by registration, dummy Argon2 hash for unknown login. Email verification 30min one-use random 43 char base64url code SHA-256; login to same account first. SMTP after DB commit, resend if failure; durable email outbox deferred.
- JWT 600s, refresh 30d absolute family lifetime, cookie DV_REFRESH scoped /api/v1/auth, CSRF DV_CSRF and X-CSRF-TOKEN, exact origin allowlist. Do not persist bearer. Current roles/approval checked DB every sensitive request. Separate tenant learner/creator/admin and global platform admin. Platform creator approval GET/PUT ETag; requires verified platform admin and target email verification. No implicit creator rights from tenant creation.
- Tenant create Idempotency-Key canonical scoped hash, current auth rechecked on replay. Invite 48h matching verified account; existing membership not silently promoted. Membership changes If-Match, last-active-admin protected by tenant row lock. Audit before/after role/status. Redis Lua using server TIME, 120/min API user, auth/credential/invite limits documented; Redis 503 fail closed. Do not store raw secrets/IP/email in audit or rate keys.
- Auth APIs /api/v1/auth/{csrf,register,login,resend-verification,verify-email,refresh,logout}; /me; /tenants, /tenants/{tenantId}, /members, /invitations; /invitations/accept; /tenants/{tenantId}/creator-capability; /admin/users/{userId}/creator-approval; /.well-known/jwks.json at Core root. Exact methods/current schema see OpenAPI. Missing If-Match 428, stale 412, outsider 404, known forbidden 403, state conflict409.

Concurrency evidence: refresh A holds family row lock, rotates and commits. B with same old token waits, observes used_at, revokes entire family and commits before HTTP401 REFRESH_REPLAY; newly issued token cannot refresh. Returning failure result rather than throwing inside transaction prevents rollback of revocation. Actual two-request test one200/one401, successor401, DB revoke and audit. Same-key concurrent tenant create two201 with same ID; concurrent two active admin self-demotions one200/one409 and one active remains. Client single-flight, Web Locks same-origin, no auto retry ambiguous mutation. Login/approval/permissions, stale version, no platform implicit membership tested.
